# ADR-0035: 文字参照で書いた波括弧は `{{ }}` の区切りにしない。エラーはノードを書いたファイルと行で報告する

- 状態: 採択（ADR-0012 / ADR-0023 を補う。置換はしない）
- 日付: 2026-11-02

## 文脈

コードレビューで、`@flat-html/vite` の式とエラーの扱いに 2 つの穴が見つかった。

### 穴 1: `{{` を文字どおりに出す書き方がない

`{{ }}` の展開は、parse5 が文字参照を戻した後のテキストと属性値に対して行う。`&#123;&#123; title &#125;&#125;` と書いても、解析の後は `{{ title }}` になり、式として評価される。`{{ }}` の記法を説明するページが書けない。ADR-0012 と ADR-0023 は、`{{` を文字どおりに出す方法を決めていない。

### 穴 2: レイアウトで起きたエラーが、ページのパスで報告される

ページをレイアウトへ合流させた後の文書には、ページと各レイアウトのノードが混ざる。式の評価と参照の展開は、この文書に対して常にページのパスで行っていた。`base.html` の 5 行目の `{{ a + b }}` は「page.html:5: 許可しない記号「+」」と報告され、`base.html` の 7 行目の解決できない `<flat-nope>` は「page.html:7」と報告された。行番号はレイアウトでの位置なので、パスと行の組がどこも指さない。ADR-0023 は、解決できない参照を、パスと行を添えて失敗させると決めている。

## 決定

### 文字参照で書いた `{` と `}` は `{{ }}` の区切りにしない（ADR-0012 を補う）

- 文字参照で書いた `{` と `}` は、`{{ }}` の区切りとみなさない。そのまま書いた `{` と `}` だけが区切りになる。新しい記法は足さない

```html
<p>&#123;&#123; title &#125;&#125; と書くと、データの title に置き換わる。</p>
```

- 対象は、parse5 が `{` か `}` に戻す文字参照のすべてである
  - 10 進の数値参照 `&#123;` と `&#125;`。先頭に 0 を付けた形も含む
  - 16 進の数値参照 `&#x7b;` と `&#x7d;`。`x` と英字の大文字小文字を問わず、先頭に 0 を付けた形も含む
  - 名前参照 `&lbrace;`、`&lcub;`、`&rbrace;`、`&rcub;`
  - 数値参照は、末尾の `;` を省いた形（`&#123`）も含む。parse5 はこれも `{` に戻す（解析エラー [missing-semicolon-after-character-reference](https://html.spec.whatwg.org/multipage/parsing.html#parse-error-missing-semicolon-after-character-reference) を出して戻す）。名前参照は、`;` を省くと parse5 が戻さないので、`;` 付きだけが対象になる
- ページ、レイアウト、テンプレートのソースのすべてに当てる。`<template html>` が差し込む値と、`{{ }}` が埋める値はデータなので当てない
- コメントと、生テキスト要素（`<script>`、`<style>` など。ADR-0033）の中身では、解析で文字参照が戻らない。そこに書いた文字参照は、どの形でも書かれたまま出す
- 出力では、区切りとみなさなかった波括弧を `&#123;` と `&#125;` にする。ブラウザは `{` と `}` として描く
- 値として使うところでは、文字参照で書いた波括弧はただの `{` と `}` である。式の中（文字列リテラルなど）、参照タグの引数、`<link rel="layout">` の `href`、テンプレートとレイアウトの資産の指定子がこれに当たる
- 資産の URL でも、文字参照で書いた波括弧は `{{ }}` の区切りにならない。資産の指定子を解決した URL を木へ書き戻すときは、URL の波括弧をすべて区切りとみなさない文字にする。集約の重複除去は、この印を戻した URL で比べるので、ページに `{` をそのまま書いた URL とも、文字参照で書いた URL とも、同じ URL なら 1 つにまとまる。`?` か `#` から後ろは解決に渡さず、書かれたまま付け直す（ADR-0034）
- 実装は次のとおりにする
  - ソースを一度そのまま解析し、コメントと生テキスト要素の中身の位置を木から求める
  - その外にある対象の文字参照を、Unicode の非文字 U+FDD0（`{`）と U+FDD1（`}`）に置き換えて、もう一度解析する。置き換えるものがなければ 2 度目の解析はしない
  - 直列化の後に、U+FDD0 と U+FDD1 を `&#123;` と `&#125;` に戻す
  - ソースに U+FDD0 か U+FDD1 が書かれていれば、そのファイルと行を添えて `TemplateError` にする

### エラーは、そのノードを書いたファイルと行で報告する（ADR-0023 を補う）

- 式のエラー（テキストと属性値の `{{ }}`、`<template>` の `if`、`each`、`html`）と、解決できない `flat-*` 参照のエラーは、エラーを起こしたノードを書いたファイルのパスと、そのファイルでの行で報告する
- ページ、レイアウト、テンプレートのどれに書いたノードも、合流や差し込みで別のファイルの木へ移った後まで、書いたファイルで報告する。`<template each>` で複製したノードは、元のノードを書いたファイルで報告する
- テンプレートに書いた、評価されない分岐の式の構文エラー（ADR-0033）も、同じくそのノードを書いたファイルで報告する
- 資産の解決のエラー（ADR-0034）は、従来どおり、その資産を書いたファイルと行で報告する
- 実装では、ソースを解析した直後に、そのソースのすべてのノード（`<template>` の中身を含む）にファイルのパスを結び付ける。エラーはノードからパスを引き、結び付いていなければ、そのとき展開しているページかテンプレートのパスを使う

## 理由

### HTML がすでに持つ書き方を使う

- 文字参照は、HTML で記号を文字どおりに書く標準の書き方である。`<` を `&lt;` と書くのと同じ形で `{` を書ける。新しい語彙を覚えなくてよい
- 文字参照で書いても、ブラウザに届けば `{` と同じに描かれる。区切りになるかどうかの違いは flat-html の展開の中でだけ意味を持ち、出力の見た目は変わらない
- 値として使うところで `{` と `}` に戻すのは、`&#123;` と `{` が HTML では同じ文字を表すからである。区切りにならないこと以外は、これまでと同じ値になる

### 置き換える位置を parse5 の木で決める

- 文字参照が戻るかどうかは、書かれた場所で決まる。コメントと生テキスト要素の中身では戻らない。ソース全体を一律に置き換えて出力で `&#123;` に戻すと、`<script>` の中の `&lbrace;` が `&#123;` に書き換わり、スクリプトの中身が変わる
- 場所の判定を自前の字句解析で持つと、parse5 と食い違う。たとえば SVG の中の `<script>` は生テキスト要素でなく、文字参照が戻る。そのまま解析した木から求めれば、parse5 と同じ判定になる

### 非文字を使う

- U+FDD0 と U+FDD1 は Unicode の非文字で、内部用に恒久的に取っておかれ、通常は交換されない（[Unicode の FAQ: Noncharacters](https://www.unicode.org/faq/private_use.html#noncharacters)）。HTML の解析でも、入力に現れると解析エラーになる（[noncharacter-in-input-stream](https://html.spec.whatwg.org/multipage/parsing.html#parse-error-noncharacter-in-input-stream)）。ソースに書かれることはまずない
- 文字参照を 1 文字に置き換えるので、改行の数は変わらず、行番号はそのまま使える。`{` も非文字も空白でない普通の文字として扱われるので、解析した木の形も変わらない

### エラーを書いたファイルで報告する

- 行番号は、ノードを書いたファイルでの位置である。パスだけを展開しているページのものにすると、パスと行の組がどこも指さない
- ADR-0023 は、誤字を黙って通さず、パスと行を添えて失敗させると決めた。書いた場所を示せなければ、レイアウトの誤字を探せない
- パスを結び付けるのは、ソースを解析した直後の 1 か所で済む。合流、差し込み、複製のどの経路を通っても、エラーを出す側はノードからパスを引くだけでよい

## 却下した選択肢

- `{{ '{' }}` のような式で書かせる: 技巧的で読みにくい。`}}` を含む文字列は、最初の `}}` で式が終わるので書けない
- `<pre>` や `<code>` の中は展開しない: 要素の種類で式の有無が変わる暗黙の規則になる。`<pre>` の中で値を埋めたいときに埋められなくなる
- 独自のエスケープ記法（`\{{` など）を足す: 新しい語彙になる。HTML としては `\` と `{{` が並ぶだけで、flat-html を知らないと意味が分からない
- ソース全体の文字参照を一律に置き換える: コメントと生テキスト要素の中の `&lbrace;` などが、出力で `&#123;` に書き換わる
- 置き換える位置を自前の字句解析で決める: parse5 の判定と食い違う
- エラーのパスを、展開しているページのパスにする（従来の実装）: パスと行の組がどこも指さない

## 影響

- `{{ }}` の記法を説明するページで、`&#123;&#123; title &#125;&#125;` と書けば `{{ title }}` と表示される
- これまで文字参照の波括弧で書いた `{{ }}` を式として評価させていたソースは、式が評価されず、書かれたまま出る
- 出力では、テキストと属性値の中の文字参照の波括弧が `&#123;` と `&#125;` の形にそろう。`&lbrace;` などで書いても `&#123;` になる。コメントと生テキスト要素の中は書かれたまま出る
- 参照タグの引数に文字参照で書いた波括弧は、テンプレートの中では `{` と `}` の値になる。`{{ }}` で埋めた結果には `{` と `}` がそのまま出る。描かれ方は変わらない
- テンプレートとレイアウトの資産の URL に文字参照で書いた波括弧（`./&#123;&#123;x&#125;&#125;.css`）は、解決の後も式として評価されず、出力では `&#123;` と `&#125;` になる。解決した URL の波括弧は、ファイル名にそのまま書かれた `{` と `}` も含めて、出力では `&#123;` と `&#125;` になる。描かれ方と、Vite が読む URL は変わらない
- ページに書いた `/a{b}.css` と、テンプレートやレイアウトの `./a{b}.css` を解決した `/a{b}.css` は、同じ文字列になり、重複除去（ADR-0013）で 1 つにまとまる
- ソースに U+FDD0 か U+FDD1 を書くと、変換が失敗する
- データ（`data` と、それを `{{ }}` や `<template html>` で埋めた値）に U+FDD0 か U+FDD1 が含まれると、出力では `&#123;` か `&#125;` になる
- SVG と MathML の中の CDATA 区間（`<![CDATA[ … ]]>`）では、解析で文字参照が戻らないが、置き換えの対象から除いていない。parse5 は CDATA 区間を普通のテキストとして直列化するので、区間に書いた波括弧の文字参照は、出力で `&#123;` と `&#125;` になって `{` と `}` として描かれる。置き換えなければ `&amp;#123;` と出て、`&#123;` という文字列として描かれる
- レイアウトに書いた式と参照のエラーは、レイアウトのパスと行で報告される。ページに書いたものは、レイアウトへ合流した後もページのパスと行で報告される
- ページの `<html>` と `<body>` の属性は、レイアウトの `<html>` と `<body>` へ合流する（ADR-0019）。合流した属性の式のエラーは、レイアウトのパスと、レイアウトの `<html>` か `<body>` の行で報告される
